# FAQ

### What can Unknot change in my repository?

By default, nothing in your source. In `plan` mode (the default) it writes only under `.unknot/` (state, campaigns, slices, decisions, decompositions) and, for `/unknot:architecture`, documentation under `.unknot/docs/architecture/`. Source changes happen only after you have raised the mode to `assist` or higher in an accepted config, a human has approved a specific slice, and then only inside that slice's git worktree (`.unknot/worktrees/<slice>/`) and its declared scope. Your main checkout is not edited. Unknot never merges, pushes or opens a pull request. You do that from the slice branch.

### Why does it say my config "has never been accepted" and run in plan mode?

A config file can raise Unknot's authority (mode, approvers, commands), so a file that just appeared in the repository is not trusted. Run `unknot config diff`, then `unknot config accept` in a separate terminal window (Claude Code's `!` prefix is not interactive; if `unknot` is not found there, see `unknot cli install`). If you edit `config.yaml` afterwards, or a merge changes it, the accepted version stays in force and only changes that tighten policy (lower mode, smaller limits, more protected paths) apply until you accept again. Details in [configuration.md](configuration.md#acceptance).

### Can Claude approve its own work?

No. `unknot approve` needs an interactive terminal and the passphrase of your approver key, which it reads from `/dev/tty`. An agent's shell has no TTY, the command refuses when it detects Claude Code (the message says which: no terminal, or an agent session), and the hooks refuse the verb outright. An approval is an Ed25519 signature over the commit, the slice, the exact diff and the policy digest, so approving a plan does not approve a different diff. See [security-model.md](security-model.md#approvals).

### I lost my approver passphrase, or my key. What now?

There is no recovery of the private key; the passphrase protects it. Generate a new one (`unknot keys generate <new-name>`), register its public key in the config, accept the config, and re-approve. Approvals signed by the old key can be revoked by removing the approver from the config: an approval is only valid while its approver is still registered and holds the role. Keep approver keys in the backup process you use for any signing key (they are outside `unknot backup`).

### Does Unknot send my code anywhere?

Unknot itself makes no network requests by default (`limits.max_network_requests: 0`), and brokered commands run with the network off. It has no telemetry unless you turn it on, and then only counts, durations and ids go to a file or an endpoint you allowlist. But Claude Code is the host: whatever Claude reads in your repository goes to the model as in any Claude Code session. Unknot restricts what the model may read during an Unknot run (inside the project, not credential paths), but it does not change where Claude Code sends the content. If the repository cannot be seen by the model at all, Unknot is not the right layer.

### How do I know the tests actually ran?

Every check Unknot counts is a command it ran itself through the broker, and the evidence record is written by the runtime: the exact argument vector, working directory, exit code, whether it timed out, the sandbox in effect, and SHA-256 of the complete stdout and stderr. The records are in the proof bundle's `command-log.jsonl` and the ledger. The model cannot mark an obligation passed. If there is no `test_unit` command, the obligation says a human must confirm, and the slice cannot reach `REVIEW_READY` until someone attests it. Passing tests is evidence, not proof of equivalence, and the bundle lists what remains uncertain.

### Why did `decompose` say "retain"?

Because that is the least risky correct answer when nothing both fits the evidence and serves a recorded driver. Read `rejected_treatments` and `evidence_gaps` in the DEC file. Common reasons: no driver recorded (service extraction and micro-frontends are not offered without one); no table access facts, so shared-table writers is unknown; no runtime traces; no CODEOWNERS, so ownership alignment is unknown; a candidate that is not stable under perturbation. A few inputs the pattern cards ask for (API client counts, route navigation) are not measured, so some treatments cannot be selected; see [decomposition.md](decomposition.md#how-a-treatment-is-chosen). Record a real driver, supply the missing evidence, and run again.

### A finding is wrong, or true but not worth fixing. What do I do?

`/unknot:reject F-0042 --rationale "generated by our codegen" --days 180` suppresses it for 180 days (default 90); `/unknot:accept` records that it is real and will be left as it is. Both need your own prompt; an agent cannot record them unprompted. Decisions go to `.unknot/decisions.jsonl` and feed calibration: detectors whose findings you keep rejecting rank lower, and `unknot learn propose` may suggest a higher threshold for a human to accept ([learning.md](learning.md)). For findings caused by generated code, add the path to `generated_paths` or `scope.exclude` instead.

### Does it work on Windows? Without a sandbox?

Linux and macOS are tested in CI. Windows is not tested; use WSL2. The OS sandbox is `sandbox-exec` on macOS and `bwrap` on Linux. Without one, brokered commands (your test suite) run unconfined; `unknot doctor` warns, and `security.require_os_sandbox: true` makes Unknot refuse to run them. The mapper, diagnosis and planning do not need the sandbox. See [SECURITY.md](../SECURITY.md).

### Can it work on a repository with no tests?

It can map, diagnose, plan and report. For a change that should preserve behaviour, the plan puts a `characterization` slice first (tests that pin current behaviour), and any obligation that would need a missing command becomes a human attestation. Without a `test_unit` command `unknot apply` skips the baseline check and says that behaviour preservation will need human attestation. It will not pretend the change is safe.

### How large a repository can it handle?

Measured on one machine (Apple M1 Max, Node 22): a 1,000-file fixture maps cold in 1.6 seconds, and 10,000 files in 29 seconds with 569 MB peak memory; re-mapping after a 5-file commit took 7 seconds at 10,000 files. Cold mapping time grew faster than linearly between those sizes. 100,000 files has not been measured. Results depend on your languages, adapters and history length. See [benchmarks.md](benchmarks.md) and use `node scripts/bench.mjs --large` on your own hardware.

### What if the repository contains instructions aimed at the AI?

Repository text and tool output are data. A comment saying "ignore previous instructions" does not change what Unknot permits, because every action goes through the policy decision point and authority comes from the run, the mode, the approved slice and the capability, not from anything the model read. The `PostToolUse` hook also records suspected injection attempts in the ledger and reminds the model that the content is data, but that is a nudge. Unknot's agents are told to mention such text in their reports instead of acting on it.

### How do I undo something?

Before acceptance, `/unknot:rollback UK-0007` removes the worktree and branch; your checkout was never touched. After acceptance, `unknot rollback UK-0007` needs a rollback-stage approval, then prepares a `git revert` on a new branch `unknot/UK-0007-rollback` for you to review; nothing is pushed. That works when the slice's recovery type is `revert`. Slices whose recovery is `roll_forward`, `restore`, `fail_over`, `recreate` or `compensate` refuse and point at `recovery.md` in the proof bundle, because a source revert is not the right undo. Unknot does not undo changes outside the repository, such as a deployed migration.

### Which files in `.unknot/` should I commit?

`config.yaml`, `campaigns/`, `slices/`, `decisions.jsonl`, `decompositions/` and documentation under `.unknot/docs/` are meant to be committed. `.unknot/.gitignore` (created for you) excludes `state/`, `cas/`, `runs/`, `worktrees/`, `telemetry/` and `config.proposed.yaml`. The ledger and encrypted artifact cache live in `state/` and `cas/`; proof bundles are in `runs/`. Keys are not in the repository at all; they are in `$UNKNOT_HOME` (default `~/.config/unknot`). Back up Unknot's state with `unknot backup` and escrow the keys separately ([operations.md](operations.md)).

### Can I run it in CI?

Analysis commands (`map`, `diagnose`, `decompose`, `doctor`, `status`) work in CI; they change nothing in your source, only Unknot's own state. In a pipeline the actor is recorded as `ci:pipeline`, which can never satisfy a human-only check, so approvals cannot be given from CI. `unknot daemon` exposes an API that deliberately has no approve endpoint. Treat a CI job as an analyst, not an approver.

### How do I enforce settings across a company?

Ship a signed organization policy bundle (`org-policy.yaml` plus a detached Ed25519 signature) in a managed directory. Repositories can tighten it but not loosen it: the lower mode wins, limits take the smaller value, protected paths are unioned, approval roles are added, and `approvers_locked` can fix the approver list. Organization-only keys: `max_mode`, `approvers_locked`, `forbid_executables`. See [configuration.md](configuration.md#organization-policy). Note that in this version only the keys listed there are merged; org policy for other keys has no effect.

### Why does `unknot doctor` warn that no approvers are registered?

Because no slice can be approved until at least one approver is in the accepted config. Run `unknot keys generate <name>`, paste the block it prints into `.unknot/config.yaml` (or the proposal), and `unknot config accept`.
